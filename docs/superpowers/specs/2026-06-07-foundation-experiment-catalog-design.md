# Foundation Experiment Catalog Design

Status: draft for user review
Date: 2026-06-07

## Goal

Create a versioned experimental catalog that turns EDA evidence into concrete,
auditable experiments for the next project phases, with baseline improvement as
a first-class objective.

The catalog must prevent the next waves from ignoring the knowledge already
generated by Onda 2E. It should make every proposed baseline, regime, feature,
threshold, or validation experiment traceable back to EDA evidence and
comparable against an explicit baseline.

## Context

Onda 2E now produces a rich evidence surface:

- `reports/onda2e/evidence_decision_register.csv`
- `reports/onda2e/regime_design_queue.csv`
- `reports/onda2e/domain_thesis_evidence.csv`
- domain artifacts for timing, cooling, foehn, wind, and regime architecture
- `reports/regime-design/*` candidate-regime validation artifacts

This solved the earlier problem of an EDA backlog with unresolved theses. The
new problem is different: downstream waves still primarily consume
`data/features.parquet`, `data/labels.parquet`, and
`validated_feature_contract.json`. That means the EDA can remain outside the
implementation path unless there is an intermediate contract for experiments.

The project also needs a stronger baseline loop. A baseline is not only a
minimum score to beat; it is a diagnostic instrument. The project should use
baseline failures to discover weaknesses, link them to EDA evidence, and test
improvements before model work resumes.

## Scope

This design introduces a Foundation Experiment Catalog. The first version will
produce machine-readable and human-readable artifacts under:

- `reports/foundation-experiments/foundation_experiment_catalog_v1.csv`
- `reports/foundation-experiments/foundation_experiment_catalog_v1.md`

The catalog includes experiments in these families:

- `baseline`: improve or split L0-L4/null comparators;
- `regime`: revise or validate candidate regime assignment;
- `feature`: probe a causal feature inspired by EDA;
- `threshold`: calibrate or replace fixed diagnostic thresholds;
- `validation`: add a robustness, ablation, or stratified validation check.

Every row is an experiment candidate, not a production promotion.

## Non-Scope

- Do not train Onda 3 models.
- Do not promote any feature, regime, or baseline to production.
- Do not overwrite `data/features.parquet`.
- Do not replace ADR-012 decisions.
- Do not add external data sources.
- Do not relax Onda 4 gates.

## Core Principle

EDA evidence must flow into implementation through experiments, and every
experiment must answer:

1. What weakness or opportunity does this address?
2. Which EDA artifact supports trying it?
3. What baseline or current system does it compare against?
4. What metric decides whether it helped?
5. What stops it from becoming production accidentally?

## Catalog Schema

The v1 CSV should use stable, explicit columns:

| Column | Meaning |
|---|---|
| `experiment_id` | Stable ID such as `BEXP-L2-MONTH-REGIME-001`. |
| `experiment_family` | `baseline`, `regime`, `feature`, `threshold`, or `validation`. |
| `domain` | `BASELINE`, `TIMING`, `COOLING`, `WIND`, `FOEHN`, `REGIME`, etc. |
| `source_decision_id` | ADR-012 decision ID or rule ID that motivates the experiment. |
| `source_artifacts` | Semicolon-separated evidence artifacts. |
| `weakness_target` | Failure mode addressed: `dead_regime`, `high_mae`, `fixed_threshold`, `sparse_cell`, `drift`, `nowcast_risk`, etc. |
| `candidate_surface` | Where the experiment would run: `baseline_ladder`, `feature_builder`, `regime_assignment`, `validation_harness`, `leaderboard`, or `robustness`. |
| `implementation_kind` | `new_baseline`, `baseline_variant`, `feature_probe`, `regime_revision`, `threshold_calibration`, `stratified_validation`, or `ablation`. |
| `input_columns_or_artifacts` | Required columns or artifact files. |
| `strata` | Month, CP, regime, wind sector, cooling mechanism, or other splits. |
| `causal_status` | `causal_available`, `outcome_only`, or `audit_only`. |
| `leakage_risk` | Short statement of leakage risk and guard. |
| `power_warning` | Sample-size or sparse-cell warning. |
| `baseline_comparator` | Current comparator: `L0`, `L1`, `L2`, `L4`, `current_best`, or specific baseline. |
| `success_metric` | `mae_delta`, `ci_lo`, `dead_regime_count`, `passing_years`, `fallback_rate`, etc. |
| `acceptance_gate` | Exact condition required for the experiment to advance. |
| `stop_condition` | Condition that rejects or parks the experiment. |
| `production_status` | Always `EXPERIMENT_ONLY` in v1. |
| `next_action` | Concrete next implementation or validation step. |

## Baseline Experiments

Baseline experiments are first-class entries because the project needs strong
comparators before model work. The baseline ladder should become a living
experimental surface, not a frozen afterthought.

Initial baseline experiment examples:

- `BEXP-L2-MONTH-REGIME-001`: month/regime climatology baseline compared
  against current L2 day-of-year climatology.
- `BEXP-L4-MONTH-CP-REGIME-001`: empirical conditional baseline stratified by
  month, CP, and candidate regime, compared against current L4.
- `BEXP-LATE-TMAX-Q90-001`: late-Tmax risk baseline using train-only
  month/regime q90 timing norms, compared against fixed late-hour diagnostics.
- `BEXP-COOLING-MECHANISM-001`: baseline adjustment for cooling mechanism and
  CP, compared against L0/L4 and the current fixed cooling comparator.

Each baseline experiment must report whether it reduces MAE, exposes a
repeatable weakness, or fails. A failed baseline experiment still has value
because it prevents model work from chasing a weak or leaky idea.

## EDA-Driven Experiments

EDA-driven experiments translate supported/adapted/promoted decisions into
testable implementation candidates.

Initial experiment examples:

- `REXP-DEAD-MARITIME-001`: repair `candidate_maritime_cloudy` because R2
  screening still marks it as dead.
- `REXP-DEAD-MIXED-001`: split or merge `candidate_mixed_or_transition`
  because it is dead in candidate R2.
- `TEXP-COOLING-MECHANISM-001`: replace the fixed `-2 C/h` cooling threshold
  with mechanism/month/CP calibration.
- `FEXP-FOEHN-CONTINUOUS-001`: test continuous or binned `foehn_score` instead
  of fixed `foehn_score > 60`.
- `WEXP-SOUTHERLY-DEPTH-001`: test southerly count/depth as a regime-design
  split using wind-sector reliability artifacts.

## Data Flow

The intended loop is:

```text
EDA artifacts and ADR-012 decisions
  -> foundation_experiment_catalog_v1.csv
  -> selected manual or CLI experiment implementation
  -> foundation_experiment_results_v1.csv
  -> leaderboard and robustness comparison
  -> ADR-012 decision update
```

The catalog is not itself a gate pass. It is the missing bridge between
descriptive EDA and implementation work.

## Selection Policy

The v1 catalog should not include all 245 supported local thesis decisions as
individual experiments. That would recreate the original overload.

The first catalog should include a curated, mechanically generated priority set:

- every item in `regime_design_queue.csv`;
- every quarantined baseline comparator;
- every generated repair candidate artifact row;
- every R2 dead candidate family;
- baseline experiments needed to compare future improvements;
- a small number of feature/threshold probes with clear causal availability and
  power.

This keeps the catalog useful as an action surface rather than another archive.

## Results Schema

A later results artifact should use:

| Column | Meaning |
|---|---|
| `experiment_id` | ID from the catalog. |
| `run_id` | Stable run timestamp or hash. |
| `status` | `not_run`, `running`, `passed`, `failed`, `blocked`, or `superseded`. |
| `result_artifact` | CSV/MD/JSON produced by the experiment. |
| `baseline_mae` | Comparator MAE when applicable. |
| `candidate_mae` | Candidate MAE when applicable. |
| `effect_size` | Primary improvement or degradation. |
| `ci_lo` | Lower confidence bound when available. |
| `ci_hi` | Upper confidence bound when available. |
| `n_rows` | Rows evaluated. |
| `n_years` | Years evaluated. |
| `r2_dead_regimes` | Dead regimes after experiment when applicable. |
| `decision_update` | ADR-012 decision update path or empty. |
| `notes` | Short interpretation. |

## Error Handling

The catalog builder should fail only when required core inputs are missing or
schema-invalid. Optional domain artifacts should be recorded as warnings in the
markdown report.

Validation errors should be explicit:

- missing source artifact;
- source artifact has zero rows;
- unsupported decision status;
- experiment has no comparator;
- experiment lacks a success metric;
- experiment would require outcome-only data as a CP feature.

## Testing

Tests should cover:

- building catalog rows from ADR-012 queues;
- baseline experiments generated from quarantined baseline rules;
- R2 dead candidate families becoming regime repair experiments;
- no production status other than `EXPERIMENT_ONLY`;
- rejected items do not become experiments unless the experiment is an explicit
  negative control or ablation;
- markdown report summarizes counts by family, domain, weakness target, and
  candidate surface;
- missing optional artifacts create warnings rather than silent drops.

## Acceptance Criteria

The design is implemented when:

1. `foundation_experiment_catalog_v1.csv` exists and has at least one baseline
   experiment and one EDA-driven regime experiment.
2. Every row has a source artifact, comparator, success metric, acceptance gate,
   stop condition, and `production_status = EXPERIMENT_ONLY`.
3. `foundation_experiment_catalog_v1.md` explains the priority experiments and
   why they are not production changes.
4. The catalog includes experiments for the two current dead candidate families:
   `candidate_maritime_cloudy` and `candidate_mixed_or_transition`.
5. The catalog includes baseline-improvement experiments that can later be
   compared through leaderboard or robustness artifacts.
6. Tests and lint pass.

## Implementation Defaults

The first implementation should use these defaults unless the implementation
plan later finds a concrete conflict:

1. Expose the catalog through a dedicated CLI command,
   `tmax foundation-experiments`, so it can be rerun independently from the
   heavier `tmax onda2e` pipeline.
2. Generate all mechanically justified priority rows from the selection policy,
   but the markdown report should highlight the top-priority subset by weakness
   target and candidate surface.
3. Catalog v1 writes the catalog CSV and markdown report only. The follow-on
   results runner writes `foundation_experiment_results_v1.csv` after executable
   experiment rows exist; it must never create production promotions.
